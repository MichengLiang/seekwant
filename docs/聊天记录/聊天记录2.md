# AI 小说转剧本工具：这个甲方到底要什么？

我先说结论：这份 `资料1.md` 不是一个完整产品需求书，而是一道非常收窄的“AI 内容结构化转换”任务。它真正要求交付的当前对象，不是 Final Draft 那种成熟编剧软件，不是 Toonflow/LumenX 那种短剧一站式生产平台，也不是直接出视频的 AI 漫剧系统，而是：

> 输入至少 3 个章节的小说文本，自动生成一份结构化、可编辑、可校验的 YAML 剧本初稿；同时写一篇文档定义这个 YAML Schema，并解释为什么这样设计。

这句话里，“AI 辅助剧本创作工具”是愿望层表达；“降低改编门槛、提升效率”是目标线索；真正可验收的是“3 章以上小说文本 → 结构化剧本 YAML + Schema 文档”。所以如果我们按照观察、判断与行动那套框架来拆，当前人工制品的边界应当非常清楚：它是一个把小说叙事材料转成剧本中间表示的工具，而不是完整影视工业工作台。

## 一、题面里已经成立的事实、愿望、需求与方案边界

本地材料只有一句题面：

“很多小说作者希望将自己的作品改编成剧本，请开发一款 AI 辅助剧本创作工具，降低改编门槛，提升效率。要求：能将 3 个章节以上的小说文本自动转换为结构化剧本（YAML 格式），让作者可以快速获得可编辑、可进一步打磨的剧本初稿。请额外写一篇文档，定义剧本的 YAML Schema。文档中需说明该 Schema 的设计原因。”

严格拆开看：

1. 事实层：存在小说作者希望把作品改编成剧本。题面没有给用户访谈、行业数据、具体作者场景，所以这只是甲方给出的领域假设，不是我们独立验证过的用户事实。

2. 愿望层：降低改编门槛、提升效率。这里没有指标，比如节省多少时间、多少字、多少章节、保留多少情节、角色一致性如何验收。

3. 需求层：作者要快速获得“可编辑、可进一步打磨”的剧本初稿。这比“自动生成好剧本”稳得多。它不是要求一次成片级剧本，而是要求生成可修改的初稿。

4. 规约层：输入是 3 个章节以上小说文本，输出是 YAML 格式的结构化剧本，还要有 Schema 文档。

5. 当前边界：题面没有要求账号系统、多人协作、在线编辑器、导出 PDF/FDX、分镜图、TTS、视频生成、商业版权管理、短剧投流数据、剧本评估模型、素材资产库。这些都可能是相邻对象，但没有自动进入当前对象。

所以这个甲方真正要的东西，大概率是“AI 小说改编剧本的结构化转换器”。它的核心价值不是排版，而是把小说中的章节、场景、人物、叙事、对话、动作、内心描写和旁白，转换成一个剧本系统可以继续编辑、校验、导出或进入后续生产链的中间数据结构。

YAML 这个要求非常关键。正常影视编剧最终交付给人看的不是 YAML，而是 Final Draft、PDF、Fountain、Word 或制片部门能用的剧本格式。甲方偏偏要求 YAML，说明验收重点不是“像不像排版剧本”，而是“结构化是否稳定、机器是否能读、作者是否能编辑、后续是否能扩展”。也就是说，YAML Schema 是这个任务的公共契约。

## 二、市场上有没有类似的？有，而且方向很明确

我查了几类对象：传统商业编剧软件、AI 写作工具、AI 编剧/前期制片工具、开源短剧生产平台、专门小说转剧本项目、剧本格式生态。

### 1. 传统商业编剧软件已经跑通，但它们不是“小说转剧本”

Final Draft、Celtx、WriterDuet 这类产品商业上非常成熟。Final Draft 官方强调的是自动按行业标准格式化剧本、Beat Board、Outline Editor、修订、评论、版本保存、导出 PDF。Celtx 官方强调多格式脚本编辑、故事板、Beat Sheet、剧本拆解、shot list、call sheet、预算、协作和制片前期。

这说明“剧本创作软件”这个市场是成立的，专业作者和制片流程愿意为格式、协作、修订、制片衔接付费。但这些成熟产品的核心不是“把小说自动改编成剧本”，而是“人在专业格式和生产流程里写剧本”。它们解决的是剧本写作后的专业工作流，不是小说改编的最前端。

对我们来说，Final Draft/Celtx 的意义是给 Schema 设计提供反向约束：真正可用的剧本结构至少要能表达场景、动作、人物、台词、旁白、转场、备注、修订等对象。否则 YAML 虽然能生成，但无法进入成熟剧本生态。

证据坐标：
- Final Draft 13 官方页：https://www.finaldraft.com/products/final-draft-13
- Celtx 官方页：https://www.celtx.com/

### 2. AI 写作工具跑通的是“小说创作辅助”，不是直接改编链条

Sudowrite、Novelcrafter 这类工具说明 AI 辅助长篇创作本身已经有用户和订阅模式。Sudowrite 的定位是 fiction AI writing partner；Novelcrafter 强调 Codex、角色资料、系列共享资料、AI brainstorming/writing/reviewing，并且支持 novels、screenplays 等形式。

它们说明作者愿意为 AI 写作辅助付费，尤其是构思、续写、资料库、人物一致性、审稿这类能力。但它们不是题面这个对象的直接替代品。小说转剧本需要做叙事媒介转换：小说可以有大量心理描写、旁白、自由间接引语、叙述者声音；剧本要把这些变成可拍、可演、可说、可剪的场面、动作和台词。这个转换不是普通续写。

证据坐标：
- Sudowrite 官方页：https://www.sudowrite.com/
- Novelcrafter 官方页：https://www.novelcrafter.com/

### 3. AI 编剧/前期制片工具说明“剧本结构化之后的下游”有明确价值

NolanAI/FinalBit、Filmustage 这类工具强调 AI screenwriting、script breakdown、budgeting、scheduling、storyboards、shot lists、VFX breakdown、script analysis、synopsis 等。它们的价值链是：有剧本之后，自动分析、拆解、预算、排期、分镜、制片管理。

这对题面的启发很重要：如果我们输出的 YAML 只是把小说文本换个容器装起来，下游无法拆解，就没有太大价值。好的 YAML Schema 应该天然支持后续 script breakdown：角色、场景、道具、时间、地点、动作、对白、情绪、冲突、镜头/分镜线索、原文来源引用。哪怕当前不做分镜和预算，也要保留这些结构位点。

证据坐标：
- FinalBit/NolanAI 官方页：https://www.finalbitai.com/
- Filmustage 官方页：https://filmustage.com/

## 三、开源社区有没有可复用轮子？有，但要分清“能复用什么”

### 1. Dramatron：AI 编剧结构生成的经典参考，不是小说改编器

Google DeepMind 的 Dramatron 仓库定位是用大语言模型生成 coherent scripts and screenplays。它有 1000+ GitHub stars，Apache-2.0 许可。Dramatron 的核心启发是分层生成：先有 logline、characters、plot、locations，再生成 dialogue 等。它说明 AI 编剧不是一次性让模型吐完整剧本，而是应该先生成结构，再逐步展开。

但 Dramatron 是从提示和故事构思生成剧本，不是从长篇小说章节抽取并改编。它可以提供架构思想，不能直接解决“忠于原文、保留章节事件、处理长文本上下文、输出 YAML Schema”的要求。

证据坐标：
- GitHub：https://github.com/google-deepmind/dramatron

### 2. Fountain/afterwriting：剧本格式生态，可以作为导出层参考

Fountain 是 plain text markup language for screenwriting，强调纯文本、可移植、未来兼容、适合早期创作。Fountain 官方明确说它支持剧作者早期创作需要的内容，但不包含完整生产阶段功能。afterwriting-labs 是 Fountain screenplay 的后处理工具。

这说明如果未来要把 YAML 变成作者熟悉的剧本稿，Fountain 是很好的导出格式候选。当前任务要求 YAML，所以不应把 Fountain 当主存储；但 Schema 可以设计得容易导出到 Fountain：场景标题、动作、角色名、对白、括注、转场这些结构要清楚。

证据坐标：
- Fountain 官方：https://fountain.io/
- afterwriting-labs：https://github.com/ifrost/afterwriting-labs

### 3. Toonflow：最接近“小说 → 短剧/视频链条”的开源产品

Toonflow 是非常关键的参照。GitHub 描述是“开源一站式 AI 短剧创作工具，将小说、剧本快速转化为动画短剧；集成 AI 编剧、智能分镜、角色与视频生成”。它有约 9600 stars、1700+ forks，README 里明确写了“章节事件图谱驱动改编”“自动提取原著章节事件并结构化存储，剧本改编按事件图谱精准调用上下文，减少长文本信息丢失”。

这和题面高度相关。它说明真正做小说改编，核心难点不是“让模型写点台词”，而是：长文本章节事件如何抽取、如何形成事件图谱、如何保持上下文、如何让改编策略调用原文信息。Toonflow 还把后续链条接到分镜、角色、素材和视频，所以它证明了这个方向在开源社区已经有完整工作流探索。

但 Toonflow 太大了。题面没有要求我们实现无限画布、Agent 记忆、视频模型、图片模型、桌面客户端、素材库。我们能借鉴的是工作流思想：先抽取章节事件，再生成故事骨架/改编策略，再输出结构化剧本。不能照搬整个产品边界。

证据坐标：
- GitHub：https://github.com/HBAI-Ltd/Toonflow-app

### 4. LumenX：阿里系开源，证明“剧本分析 → 资产 → 分镜 → 视频”链条存在

LumenX Studio 定位是 AI 短漫剧一站式生产平台，说明它能将小说文本转化为动态视频，并打通剧本分析、角色定制、分镜绘制、视频合成。README 里工作流是：资产提取 → 风格定调 → 资产生成 → 分镜脚本构造 → 分镜图生成 → 分镜视频生成。它强调深度剧本分析、自动提取角色/场景/道具、生成专业分镜脚本。

这再次说明 YAML Schema 的重要性：如果我们要让剧本初稿“可进一步打磨”，结构化对象不应只有 scenes/dialogues，还应能表达角色、场景、道具、情绪、视觉提示、原文依据。这些字段不是为了炫技，而是为了后续动作：作者修改、AI 二次改写、分镜抽取、角色资产生成。

证据坐标：
- GitHub：https://github.com/alibaba/lumenx

### 5. 专门 Novel-to-Script 项目：证明学生/个人项目已经在做，但质量参差

我查到 `ZhengDongHang/Novel-to-Script`，它是一个基于 DeepSeek API 的小说转剧本转换器，辅助 BERT 情绪分析、Seq2Seq 动作分析，最后生成 Word 剧本。它有 15 stars，说明这是小型个人项目，不是成熟生态。但它很有参考价值：它把动作分析、情绪分析、结构化数据转剧本作为中间步骤，这和题面的 YAML 思路一致。

另外 GitHub 上今天还出现了很多“AI 小说转剧本工具”“小说转剧本 YAML”之类零星仓库，更新时间集中在 2026-06-05，很多 0 stars。这很可能是同一赛题/作业/招标题传播导致的提交潮。它们只能证明这个题面正在被多人实现，不能证明商业模式成熟。

证据坐标：
- Novel-to-Script：https://github.com/ZhengDongHang/Novel-to-Script

## 四、商业模式有没有跑通？要分两层说

### 1. “剧本软件”商业模式跑通

Final Draft、Celtx、WriterDuet 这类老产品已经证明：专业剧本写作、格式化、协作、修订、制片衔接可以付费。这个市场存在很久，且和影视生产流程绑定。

但它们不能证明“自动小说转剧本”已经跑通。它们证明的是作者/制片方愿意为剧本工作流付费。

### 2. “短剧内容生产和消费”商业模式正在高速跑通

Sensor Tower 2025 short drama apps 报告显示，2025 Q1 全球短剧 App 内购收入约 7 亿美元，接近 2024 Q1 的 4 倍；自 2024 年以来全球累计内购收入约 23 亿美元。ReelShort 和 DramaBox 在 2025 Q1 分别达到约 1.3 亿美元和 1.2 亿美元内购收入，累计收入分别约 4.9 亿美元和 4.5 亿美元。注意这个数据还排除了广告、第三方安卓商店和官网直接支付。

这说明短剧消费侧付费非常强，尤其海外 short drama app 的 IAP 模式已经跑出规模。内容平台需要持续供给大量短剧，剧本和 IP 改编是供应链上游。所以“把小说快速改成可生产剧本”的需求在产业链里有合理性。

证据坐标：
- Sensor Tower State of Short Drama Apps 2025：https://sensortower.com/blog/state-of-short-drama-apps-2025

### 3. “小说转剧本工具本身”的商业模式还不能说完全跑通

这里要稳重。我们能看到 Toonflow 有商业授权条款，按年销售额分级授权；能看到 LumenX、Toonflow 这种开源一站式平台有很高关注；能看到很多商业/创业产品宣传 AI 短剧、AI 分镜、AI 剧本。但这还不足以证明“单独卖一个小说转 YAML 剧本工具”已经有稳定付费市场。

更准确的判断是：

- 剧本软件付费市场：已跑通。
- AI 写作辅助订阅：已跑通。
- 短剧内容消费和生产需求：强烈跑通。
- 小说 IP 改编为短剧/漫剧的生产链条：方向成立，开源和商业都在探索。
- 单点“小说转剧本 YAML 工具”：更像上游模块或赛题交付，不太像独立商业产品。

所以甲方要的东西如果是参赛/原型/内部工具，合理；如果想直接做 SaaS 收钱，当前题面太窄，必须接入编辑器、协作、导出、分镜、资产、质量评估、版权/项目管理等下游工作流，才有商业产品形态。

## 五、甲方可能不知道世界上已有更好的工具吗？很可能

从题面看，甲方只写“AI 辅助剧本创作工具”和“YAML Schema”，没有提 Final Draft、Fountain、Celtx、Dramatron、Toonflow、LumenX，也没有提短剧生产链条。说明甲方大概率不是成熟影视制片部门在写完整需求，而更像教学、竞赛、评测或早期甲方在描述一个 AI 应用题。

他们可能不知道：

1. 专业剧本写作已经有成熟格式生态：Final Draft、Fountain、Celtx。

2. AI 编剧已有 Dramatron 这种分层生成范式。

3. 中文开源社区已经有 Toonflow 这种“章节事件图谱驱动改编”的大体量项目。

4. 阿里 LumenX 已经把小说文本到短漫剧视频链条开源出来。

5. 真正商业上值钱的不是“生成一份 YAML”，而是这个 YAML 后面能不能稳定进入剧本编辑、分镜、角色资产、视频生成、制作管理、投流素材测试。

这并不代表甲方需求低级。相反，题面收得很窄，可能恰好适合做一个清晰可验收的核心模块：不做全流程，只把小说改编的结构化中间层做好。关键是我们不能被“AI 剧本工具”这几个字带偏，一上来做大而全产品。

## 六、这个工具真正应该解决的改编问题是什么？

小说和剧本之间不是格式转换，而是媒介转换。小说的很多信息不能直接放进剧本：

- 心理描写要变成可表演的动作、沉默、台词、旁白或视觉线索。
- 长段叙述要切成场景。
- 时间跳跃要变成场次、转场或旁白。
- 角色关系要显式化。
- 叙述者解释要转成冲突、行为和对白。
- 原文事件要保留来源，方便作者追溯和修改。
- 章节内部的情节顺序可能要重新剪辑成剧本节奏。

因此，好的转换器应该至少有这些中间步骤：

1. 章节解析：识别章节边界、标题、正文。

2. 事件抽取：每章提取关键事件、人物、地点、时间、冲突、因果关系。

3. 角色卡抽取：人物姓名、别名、关系、性格、目标、说话风格。

4. 场景切分：把小说叙事切成可拍/可演的场景。

5. 改编策略：决定哪些心理描写转旁白，哪些转动作，哪些压缩，哪些保留。

6. 剧本生成：生成 scene/action/dialogue/parenthetical/transition 等结构。

7. YAML 校验：保证输出符合 Schema，不是模型随便吐。

8. 可编辑性：每个结构单元最好有 id、source_refs、notes，作者能追溯原文和继续修改。

这里 YAML 不是附属格式，而是控制 AI 输出质量的核心边界。没有 Schema，模型输出就是自然语言散文；有 Schema，才有公共契约和可验证投影。

## 七、如果我们做，当前对象的合理产品边界是什么？

我建议当前边界定义为：

> 一个面向小说作者和改编者的 AI 辅助改编工具。它读取至少 3 章小说文本，抽取章节事件、角色、场景和可表演动作，生成结构化 YAML 剧本初稿，并提供 Schema 文档说明字段、约束和设计理由。它不承诺生成最终可拍摄成片剧本，只承诺生成可编辑、可校验、可追溯、可继续打磨的剧本初稿。

这个定义很重要，因为它阻止三个常见越界：

1. 不把它做成完整编剧软件。Final Draft/Celtx 已经很强，当前题面也没要求。

2. 不把它做成完整短剧生产平台。Toonflow/LumenX 已经在做，当前题面没授权视频链路。

3. 不承诺“一键优秀剧本”。AI 改编质量受原文、模型、提示词、上下文长度影响，可靠承诺应是结构化初稿，不是成品。

## 八、YAML Schema 应该怎么设计才像真的？

Schema 的设计理由应该从消费者行动出发，而不是字段堆叠。消费者包括：作者、后续编辑器、校验器、导出器、分镜/视频工具、AI 二次改写器。

我倾向的 Schema 顶层结构：

```yaml
schema_version: "1.0"
project:
  title: "..."
  source_type: "novel"
  language: "zh-CN"
  adaptation_target: "screenplay_draft"
source:
  chapters:
    - id: ch_001
      title: "..."
      order: 1
      summary: "..."
characters:
  - id: char_001
    name: "..."
    aliases: []
    description: "..."
    goals: []
    relationships: []
locations:
  - id: loc_001
    name: "..."
    description: "..."
script:
```

字段理由：

- `schema_version`：给未来迁移留边界，不让后续格式变化破坏旧文件。
- `source.chapters`：题面要求 3 章以上，必须保留章节输入和章节摘要，否则无法证明它处理了多章。
- `characters`：剧本的核心不是事件流水账，而是人物行动和台词。
- `locations`：剧本/分镜/制片拆解都高度依赖场景地点。
- `script.scenes`：剧本的基本单位应该是场景，而不是小说章节。
- `source_refs`：作者需要追溯这个场景来自哪一章哪段，否则 AI 改错后无法修。
- `elements`：用统一数组表达 action/dialogue/transition/note 等，便于保持剧本顺序。
- `warnings`：AI 对不确定信息要归档，不应伪装成事实。

如果面向短剧，还可以加入 `episode`、`hook`、`cliffhanger`、`duration_estimate`、`vertical_video_notes`。但这些不能默认进入当前必要结构，除非甲方明确目标是短剧。

## 九、实现上有哪些可复用经验？

最可靠的工作流不是“一次 prompt 生成完整 YAML”，而是多阶段结构化：

1. 用 LLM 抽取每章事件，输出严格 JSON/YAML。

2. 合并跨章节角色和地点，解决同名/别名。

3. 生成改编大纲：哪些事件保留，哪些压缩，哪些改为对白或动作。

4. 按场景生成剧本元素。

5. 用 Schema 校验输出，失败则让模型修复结构。

6. 对生成内容做质量检查：角色未定义、场景无地点、对白无说话人、source_refs 缺失、YAML 解析失败。

技术上，Python 很合适。可以用 Pydantic 定义内部模型，用 ruamel.yaml 输出可读 YAML，用 JSON Schema/Pydantic schema 生成文档依据，用 pytest 做样例验证。LLM 接入可以用 OpenAI compatible API，具体模型可配置。因为 workbench 里 Python 环境和依赖都适合。

开源轮子方面：

- Dramatron 提供分层生成思想。
- Fountain/afterwriting 提供未来导出剧本格式参考。
- Toonflow 提供章节事件图谱驱动改编的工作流启发。
- LumenX 提供剧本分析到分镜/资产的下游字段启发。
- Novel-to-Script 提供情绪/动作分析作为辅助任务的参考，但不要过度依赖 BERT/Seq2Seq，当前 LLM 足够做第一版抽取。

## 十、风险与验收标准

最大的风险不是代码，而是对象边界混乱。

风险 1：把“剧本”理解成最终专业剧本。题面只要求可编辑初稿，不要求行业终稿。

风险 2：把 YAML 当输出装饰。YAML 应该是公共契约，必须可解析、可校验、可追溯。

风险 3：模型幻觉。必须保留 source_refs 和 warnings，不能让模型虚构人物关系或剧情后假装来自原文。

风险 4：长文本上下文丢失。3 章以上已经足以暴露跨章角色/事件一致性问题，所以需要先抽取章节事件，再合并，不宜一次塞给模型。

风险 5：商业误判。短剧市场大，不等于单点 YAML 工具能直接赚钱。它更像生产链条中的基础模块。

合理验收标准应该是：

1. 输入至少 3 章小说文本能完成处理。

2. 输出 YAML 能被解析并通过 Schema 校验。

3. YAML 中至少包含章节来源、角色、地点、场景、动作、对白、旁白/备注、source_refs。

4. 每个场景可以追溯到原章节或原文片段。

5. 输出是作者能继续改的初稿，而不是一坨不可维护自然语言。

6. Schema 文档解释每个主要字段为什么存在、服务哪个消费者动作、引入什么成本、如何校验。

````markdown
## Definition

`Executor` 指具备以下特征的执行者抽象：

- 能理解意图；
- 能进行语义判断；
- 能进行推理与决策；
- 但对当前项目知识不具备稳定认知通路。

这里的“不具备稳定认知通路”同时包括：

- **availability 缺失**
  - 相关知识从未进入当前认知系统；
- **accessibility 衰退**
  - 相关知识虽曾进入认知系统，但当前无法稳定提取。

## Boundary

`Executor` 不是本体论意义上的实体分类。
它是一个功能角色。

因此，它不按“人类 / AI”做本体切分，
而按以下判据做切分：

- 是否有语义判断能力；
- 是否缺乏稳定项目知识通路。

这使同一主体在不同情境中可以切换角色：

- 在一个情境中是 project owner；
- 在另一个情境中则可能退化为 Executor。

## Covered Cases

在当前论域中，`Executor` 至少覆盖：

- 新进入项目的人类开发者；
- 长期脱离项目后返回的参与者；
- 每次会话都不具备稳定项目记忆的 LLM；
- 与当前任务之间的项目知识可及性已显著衰退的未来自己。

它不覆盖：

- 不具备语义判断能力的自动化脚本；
- 对项目知识保持稳定通路的 project owner。

## Why This Matters

一旦采用 `Executor` 作为稳定消费抽象，
系统就不再需要：

- 为人类设计一套 ontology；
- 再为 LLM 平行设计另一套 ontology。

后续的知识组织目标随之统一为：

> 让任何 Executor 都能通过外部化知识快速恢复上下文，
> 建立可工作的局部连续性，
````

# 重新看“AI 小说转剧本工具”：它不是自动魔法，而是给执行者、总编剧和结构化书稿搭一条可靠工作流

我先把我这次读到的材料和你的话放在同一个对象里讲清楚。

你现在不是在问“能不能让模型生成一份 YAML”。这句话太浅了。你在问的是：甲方题目里所谓“AI 小说转剧本工具”到底把什么现实工作压缩成了一个模糊说法？小说改编成剧本在成熟行业里本来由哪些人、哪些工序、哪些判断标准、哪些格式和哪些追溯机制共同完成？GPT、Claude、Gemini 这类模型进入以后，它们不是神秘的“AI”，而是一个特殊执行者：它能读自然语言，能做语义判断，能一次处理大量文本，但它没有稳定项目记忆，每次都像新员工，需要外部化上下文、清楚的本体、明确的工作指令和可校验输出。

所以这个题目不能按“AI 自动转换”理解。更准确的翻译是：

> 让一个缺乏稳定项目知识通路的执行者，在给定小说原文、改编规则、质量标准和结构化书写约定以后，完成一份可追溯、可审查、可继续改写的剧本初稿，并把这份初稿投影成 YAML。

这句话里，“执行者”可以是人，也可以是 GPT、Claude、Gemini、Kimi、豆包。它不是按“人类 / AI”分，而是按功能角色分：是否能理解意图、能做语义判断、能推理决策，但缺不缺稳定项目知识通路。这个抽象非常关键。因为一旦接受它，我们就不会掉进“AI 工具”的虚假特殊性里。模型不是一种免除工作流的东西；模型只是一个吞吐量高、成本低、上下文可喂入、但记忆不稳定的新员工。员工要写剧本，必须有原文、故事圣经、总编剧方向、格式规则、质量标准、审查机制；模型要写剧本，也一样。

## 一、官方题目的每一句话都在压缩现实工作

题面是：

“很多小说作者希望将自己的作品改编成剧本，请开发一款 AI 辅助剧本创作工具，降低改编门槛，提升效率。”

这句话包含三个层位。

第一层是领域事实或领域假设：很多小说作者希望作品改编成剧本。这里没有用户访谈和数据，所以它是甲方给定的前提。我们接受它作为任务前提，但不能把它扩展成“所有作者都需要完整影视生产平台”。

第二层是目标：降低改编门槛，提升效率。这里的“门槛”和“效率”没有量化。现实里门槛在哪里？不是 YAML 写法本身，而是小说到剧本之间的专业判断：哪些心理描写要外化成动作，哪些旁白保留，哪些角色合并，哪些情节删改，哪些场景能拍，哪些台词符合人物声音，哪些道具、场景、时间、预算、版权风险要显式化。效率在哪里？不是模型输出快，而是减少人类执行者反复回原文查、反复问为什么、反复手工做追溯、反复把碎片信息搬到不同工具里的摩擦。

第三层是题面指定的交付表面：3 个章节以上小说文本，自动转换为结构化剧本，YAML 格式，获得可编辑、可进一步打磨的剧本初稿，另写 Schema 文档并说明设计原因。

这段要求里最容易误读的是“自动转换”。从老板视角看，员工整理发票、写直播稿、改剧本，也像“自动”：老板给任务，员工产出结果。但从执行者视角看，没有任何自动。执行者必须读材料、理解目标、做选择、写稿、接受审查、修改。模型也是这样。所谓自动，只是把原来人类员工的一部分执行劳动转给模型完成，而不是消灭判断、消灭标准、消灭质量控制。

第二个容易误读的是 YAML。YAML 不是剧本的本体。YAML 是序列化格式，是机器数据交换表面。把同一个对象写成 JSON、TOML、YAML、XML，不改变对象本身。真正要设计的是本体：有哪些对象，哪些对象之间有什么关系，哪些字段承担什么消费者动作，哪些约束必须校验，哪些信息来自原文，哪些信息来自总编剧方向，哪些信息来自执行者推导，哪些信息是待审查假设。题面说“定义 YAML Schema 并说明设计原因”，它表面说 Schema，实质要求我们解释本体设计理由。

第三个张力是“可编辑”。如果最终只给作者一个 YAML 文件，普通作者并不会觉得这比可视化工作台更容易编辑。人类最快的编辑面通常是书稿、表格、卡片、剧本编辑器或 Web UI。YAML 更适合机器读、校验、投影和下游处理。因此合理解释是：YAML 是结构化投影，不一定是唯一创作表面。一个更稳的工作流可以让作者或执行者在 AsciiDoc 书稿里写、读、批注、交叉引用，让工具投影成 RDF/Turtle 供查询和校验，再投影成 YAML 满足甲方交付。题面只要求 YAML，不禁止我们把 YAML 视为投影结果。

## 二、小说和剧本不是同一种文本；改编不是格式转换

小说是面向读者的终端作品。剧本是面向制作系统的工作文件。两者都用文字，但文字承担的职责完全不同。

小说可以写：

“他忽然意识到，自己一直以来恨的不是父亲，而是那个无能为力的自己。窗外的雨声像二十年前那个夜晚一样，一层一层压回他的胸口。”

这段文字在小说里成立，因为小说直接服务读者的想象。它允许内心、意象、隐喻、时间折叠、叙述者声音和模糊感。小说的文字不需要让道具组知道买什么，不需要让演员知道每一秒怎么动，不需要让摄影师知道光从哪里来。小说可以保持高熵，让读者在脑内完成私人化渲染。

剧本不能这样完成同一个任务。剧本要回答：镜头里有什么？人在哪里？谁说话？谁沉默？手里拿什么？房间里有什么？雨是实拍还是声音？这个场景白天还是夜晚？这个道具是否后面还会出现？演员的动作是什么？观众能听到什么？如果要表达“他意识到自己恨的是自己”，是用台词、动作、沉默、物件、闪回、旁白，还是场景调度？这些选择都不是格式问题，而是信息论上的不确定性消除。

你用信息论讲这个是对的。小说文本把大量意义留在读者解释空间里；剧本必须把其中一部分意义压成可执行、可拍摄、可排练、可采购、可审查的低不确定性指令。这个过程不会无中生有地完成。信息熵不会免费降低。必须有执行者作出选择，必须有标准约束这些选择，必须有审查者确认这些选择是否符合整体方向。

所以“小说转剧本”更接近：

1. 从原文提取故事事实。
2. 从故事事实中建立角色、关系、地点、事件、时间线。
3. 根据总编剧或作者给出的方向决定改编策略。
4. 把高熵文学表达转成低熵视听表达。
5. 把执行者做出的选择留下来源和理由。
6. 把结果交给审查者继续打磨。

这不是“把小说对话抽出来”。那只是最低级、最容易坏的做法。真正的改编要处理内心描写、旁白、意象、角色弧光、节奏、删改、合并、视觉化、预算、连续性、下游消费者。

## 三、剧本为什么要长成那个样子：消费者决定对象形态

剧本的形态不是审美习惯。它是由消费者动作决定的公共契约。

总编剧或剧集运作人看剧本，不只是看文字好不好。他看的是整体调性、角色声音、节拍、主题、连续性、每一场戏是否服务故事。他要判断下属执行者写的场景是否偏离原著精神、是否违反人物弧光、是否破坏节奏。他需要批注、打回、统稿、重写。

作者看剧本，会关心原著是否被背叛，重要场景是否保留，人物是否失真，核心意象是否被转换成合适的视听表达。他需要看到来源：这场戏来自哪章哪段，执行者为什么这样改。

执行者看剧本和上游资料，需要知道自己负责哪一集、哪一幕、哪几个场景；需要知道必须遵守的大纲、节拍、角色设定、台词风格、禁用设定和已发生事件。

演员看剧本，主要消费台词、动作、潜台词、情绪转折、入场离场、与其他角色的关系变化。演员无法表演“命运的沉重”，但可以表演“把戒指放回桌上，停顿三秒，没有看对方”。

导演看剧本，消费调度、节奏、场面、镜头可能性和场景功能。导演需要知道一场戏为什么存在，场景开始和结束时故事状态如何变化。

摄影和灯光看场景标题、空间、时间、天气、内外景、视觉重点。一个“黄昏外景”就是完全不同的拍摄问题。

美术和道具看物理对象。小说里的“凌乱的房间”不够；剧本和拆解层要能指出桌上有旧报纸、药瓶、半截蜡烛、破相框，哪些是角色要拿的道具，哪些只是陈设。

服化看角色状态和连续性：上一场被雨淋湿，下一场衣服是否仍湿；上一场受伤，后面几场伤口状态如何。

制片看钱：夜戏、外景、群演、动物、车辆、爆破、VFX、特殊道具、版权品牌、历史场景。剧本每一行都可能转成预算。

剪辑和后期看转场、节奏、旁白、闪回、音效、VFX 标记。

法务看版权风险、品牌、真实人物、真实机构、歌曲、诗句、商标。

模型或校验器看结构：这个场景有没有来源、有没有地点、有没有参与角色、有没有未定义道具、有没有角色在同一时间出现在两个地点、有没有台词说话人不存在。

这些消费者共同决定剧本不是“文学文本”，而是多消费者公共契约。每个进入剧本的单位都要承担责任。一个道具名不是随便写的；它可能让道具组花钱。一个角色动作不是随便写的；它可能改变演员表演。一个原创场景不是随便加的；它可能偏离原著和总编剧方向。你说“每一个字都要负责”，放在剧本里尤其成立。

## 四、总编剧 / 剧集运作人不是可选角色；它是质量控制的功能位置

题面说“让作者可以获得可编辑、可进一步打磨的剧本初稿”。这句话没有提总编剧，但不代表总编剧功能不存在。

任何改编都要有一个上位质量控制位置。这个位置可以由原作者承担，可以由总编剧承担，可以由项目负责人承担，也可以暂时让模型根据给定标准生成一版“改编准则草案”。但这个位置不能消失。因为小说到剧本的每一步都在做选择：删哪段，留哪段，合并哪些角色，旁白还是动作，现实主义还是夸张短剧，节奏慢还是快，是否保留原著叙事顺序，是否加入钩子和 cliffhanger。

没有这个位置，执行者只是在随机做选择。模型尤其如此。模型可以生成看似完整的剧本，但它不知道什么是这个项目里的“好”。它只能从训练分布和当前提示中猜。要让它像员工一样工作，就必须给它上位标准。

因此，“自动转剧本”的真实工作流至少需要一个 Adaptation Brief，或者叫改编总纲、总编剧约束、质量控制文档。里面应包含：

- 改编目标：电影、剧集、短剧、广播剧、舞台剧，还是仅做初稿练习。
- 目标时长或集数：一集几分钟，三章要改成几场戏，是否有分集。
- 类型和调性：悬疑、喜剧、现实主义、爽剧、青春、玄幻。
- 受众和尺度：年龄层、暴力程度、性暗示、语言风格。
- 忠实度：严格忠于原著，还是保留核心冲突但允许重构。
- 叙事结构：三幕式、短剧强钩子、单元剧、群像、多线并行。
- 角色策略：是否允许合并角色、删角色、改名、改变人物关系。
- 旁白策略：旁白能不能用，最多用到什么程度。
- 原创内容策略：什么时候可以原创，原创必须标记理由。
- 质量标准：场景必须有冲突，场景结束状态必须变化，台词必须符合角色声音，动作必须可拍。
- 禁止事项：不能新增世界观规则，不能改变某个角色动机，不能让某道具提前出现。

这份东西不是附属文档，而是因果链上游。没有它，后面的 YAML 只是模型的一次自然语言发挥。给它以后，模型才是在规则内执行。

## 五、执行者模型改变了“AI”这个词的理解

你给的 Executor Model 可以直接用于这个题目。

`Executor` 是功能角色，不是实体分类。它包含能理解意图、能做语义判断、能推理决策，但对当前项目知识缺乏稳定认知通路的参与者。新人类员工是 Executor；离开项目很久后返回的人也是 Executor；每次会话没有项目记忆的 GPT、Claude、Gemini 也是 Executor；未来忘了上下文的自己也可能是 Executor。

这对“AI 小说转剧本工具”的含义有两层影响。

第一，模型不特殊。不要因为题目写 AI，就把工作流变成魔法。模型要干的活，本质上是一个执行者拿着资料做改编。它需要交接资料、任务说明、质量标准、输出格式和审查反馈。

第二，工具的责任不是“让 AI 自动写”，而是“让 Executor 能恢复上下文并稳定执行”。也就是说，工具真正要服务的是缺乏稳定知识通路的执行者。它要把项目知识外部化：小说原文、角色设定、世界观、事件线、总编剧标准、已写场景、批注、修订、来源关系。执行者进入以后，不靠记忆猜，而是靠这套外部化知识恢复局部连续性。

这就解释了为什么 AsciiDoc + RDF/Turtle + SPARQL 这条路有价值。它不是为了炫耀语义网，也不是为了给简单任务套复杂技术。它解决的是执行者的认知通路问题：人和模型都可以读书稿；机器可以读投影；查询可以找关系；校验可以拦错误；Git 可以保留历史；source line 可以回到原文。

## 六、AsciiDoc 书稿不是附属格式；它可能是更合适的主工作面

你指定的 `asciidoc-abundant-tree` 样本说明了一件事：普通 AsciiDoc 标题、稳定 ID、role、xref、rel、named attributes，就可以同时服务阅读、维护和工具链投影。

关键机制如下。

标题是节点。`== 配送策略` 不只是视觉标题；带上 `[#delivery-policy.section, kind=policy, status=active, owner=ops]` 以后，它成为可引用、可查询、可携带字段的结构单位。

稳定 ID 是身份。`#delivery-policy` 让这个节点有长期地址。改标题不必断引用。

role 标明节点身份。`.character`、`.scene`、`.beat`、`.source-snippet`、`.review-note` 可以让同一本书里的节点拥有稳定类型。role 一旦定义，就不能漂移。

xref 是边。`xref:capacity-rule[运力规则, rel=depends-on]` 表示当前标题下的对象依赖目标对象。没有 rel 时是普通 references；有 rel 时就是特定关系谓词。

named attributes 是表面字段。`owner=ops`、`status=active`、`space=EXT`、`time=DAY` 可以随源文档保留并投影。

payload 允许挂载更深结构。节点 payload 可以描述角色心理、预算风险、道具清单；边 payload 可以解释为什么某场景改编自某原文片段、为什么某规则约束某场景。

Turtle 投影保留 raw、路径、行号、heading line、content line、source heading、target heading、xref edge evidence。这意味着它不是只抽象成图；它还保留回源能力。一个查询结果可以回到源文件第几行。这个能力对改编非常重要，因为总编剧要问“这场戏来自哪段原文”，作者要问“你为什么这样改”。

所以，在这个题目里，YAML 可以是最终交付投影；AsciiDoc 书稿可以是执行者和作者的主工作面；TTL/RDF 可以是查询和校验的中间图；OWL/SHACL 可以提供本体和形状约束。它们的职责不同：

- AsciiDoc：人类可读、可写、可版本控制的书稿表面。
- RDF/Turtle：机器可查询的图投影。
- OWL/RDFS/SKOS：类型、层级、关系、术语和推理规则。
- SHACL/ShEx：封闭世界的数据质量约束。
- SPARQL/ARQ：查询、反查、审查、工作清单生成。
- YAML：甲方要求的结构化剧本交付表面。

这样理解以后，YAML 不再被神化。它只是一个投影目标。真正的设计对象是“剧本改编书稿的本体与投影系统”。

---

## 七、这个题目真正要设计的不是格式，而是本体

本体设计要回答：世界里有哪些对象，它们怎样成立，彼此有什么关系，哪些关系能推导，哪些约束必须满足。

针对小说改编剧本，至少有几类对象。

第一类是源材料对象。

- Novel：整部小说或输入文本集合。
- Chapter：章节。题面要求 3 章以上，所以章节是必要对象。
- SourceSnippet：原文片段，可带文件、起止行、字符范围、章节、摘要。
- SourceEvent：原文中发生的事件。
- SourceDescription：环境、心理、动作、叙述、背景说明等原文描述类型。
- SourceDialogue：原文已有对话。

第二类是故事圣经对象。

- Character：角色。
- CharacterAlias：别名、称呼。
- CharacterProfile：基础档案。
- CharacterWant/Need/Wound：人物驱动。
- VoiceProfile：说话方式。
- Relationship：人物关系。
- Faction/Organization：阵营和组织。
- Location：地点。
- Prop：道具。
- WorldRule：世界观规则。
- TimelineEvent：时间线事件。

第三类是改编控制对象。

- AdaptationBrief：改编总纲。
- ToneGuide：调性。
- QualityRule：质量规则。
- Constraint：硬约束。
- AdaptationPolicy：忠实度、旁白、原创、删改、角色合并策略。
- ShowrunnerNote：上位审查意见。
- AcceptanceCriterion：验收标准。

第四类是叙事结构对象。

- Logline：一句话梗概。
- Synopsis/Treatment：剧情梗概。
- Act：幕。
- Episode：集。
- Sequence：段落或序列。
- Beat：节拍。
- SceneCard：场景卡。
- ValueShift：场景开始和结束的价值变化。
- Conflict：冲突。
- Hook/Cliffhanger：短剧或剧集钩子。

第五类是剧本正文对象。

- Scene：场景。
- SceneHeading/Slugline：内外景、地点、时间。
- Action：动作描写。
- Dialogue：台词。
- CharacterCue：说话人提示。
- Parenthetical：括注。
- VoiceOver/OffScreen：画外音/画外说话。
- Transition：转场。
- Montage/Flashback/Dream：特殊叙事段。
- Note：作者或执行者备注。

第六类是制作拆解对象。

- CastRequirement：演员需求。
- PropRequirement：道具需求。
- SetDressing：陈设。
- Costume/Makeup：服化。
- VFX/SFX：视觉/现场特效。
- Stunt：特技。
- Extra/Animal/Vehicle：群演、动物、车辆。
- LocationRequirement：拍摄地点要求。
- BudgetRisk：预算风险。
- LegalRisk：法务风险。

第七类是协作与审查对象。

- Assignment：任务分配。
- Draft：草稿版本。
- Revision：修订。
- ReviewNote：批注。
- ReviewDecision：通过、打回、需重写。
- Rationale：为什么这样改。
- SourceTrace：来源追溯。
- Status：草稿、待审、通过、废弃。

这些对象不一定全部进入题面要求的最小 YAML。对象全集和当前交付集要区分。题面要求的是剧本初稿，不是完整制片管理系统。但 Schema 文档的设计理由必须知道全集，否则很容易把必需对象漏掉，或者把不该进入当前交付的东西提前承诺。

---

## 八、依赖关系必须从上游往下游推，不应倒置

这个题目最重要的是因果顺序。

源头事实之一是小说原文。没有原文，改编没有母体。原文可以给出事件、人物、地点、对话、心理、意象、世界观线索。

源头事实之二是改编目标和质量标准。没有总编剧约束，执行者不知道什么叫好。三章小说可以改成悬疑短剧、广播剧、舞台剧、电影片段、竖屏短剧，结果完全不同。

源头事实之三是本体和书写约定。没有稳定 role、rel、字段和 payload，执行者写出来的东西无法被查询、校验和投影。

从这些源头才能推出下游：

小说原文 + 章节边界 → SourceSnippet / Chapter / SourceEvent。

SourceEvent + Story Bible 抽取规则 → Character / Location / Prop / Timeline。

SourceEvent + AdaptationBrief → Beat / SceneCard / Outline。

Beat / SceneCard + Screenplay Rules → Scene / Action / Dialogue / Transition。

Scene + SourceTrace + QualityRule → ReviewNote / Revision / Acceptance。

Scene + Production Breakdown Rules → PropRequirement / VFX / BudgetRisk。

Book Graph → YAML Projection。

这个顺序不能反过来。不能先有 YAML 字段，再去问字段代表什么。不能先让模型写场景，再问为什么这么写。不能先导出剧本，再补来源。来源、规则、标准和对象身份必须早于执行输出。

你说“先穿鞋，后出门，再买菜”的时序依赖很贴切。总编剧定调、质量控制、原文事实、本体建模是上游；场景台词动作是中游；YAML、SPARQL 查询、审查清单、导出是下游。上游没定义，下游就是伪完整。

---

## 九、商业和开源社区证据应该如何放入这个判断

我之前查到的资料现在要重新定位。

Final Draft、Celtx、WriterDuet 证明专业剧本写作、排版、协作、修订、制片衔接是成熟市场。这些工具不是我们要重新发明的灯泡。它们告诉我们：场景标题、动作、角色名、台词、修订、批注、大纲、制片拆解等对象是行业长期稳定下来的东西。

Fountain 证明纯文本剧本格式已有成熟生态。它是 plain text markup language for screenwriting，适合早期创作和归档。它告诉我们：剧本可以有纯文本工作流，不必一开始就做重型 UI。

Dramatron 证明模型辅助剧本生成已有分层生成经验。它不是小说改编器，但它提示我们：不要一次性让模型吐完整剧本，应先处理 logline、characters、plot、locations，再生成 dialogue 等。

Toonflow 证明中文开源社区已经在做小说/剧本到短剧/动画短剧的链条，并且明确提到章节事件图谱驱动改编。这个点和我们的判断高度吻合：长文本改编要先抽取章节事件和上下文，不能直接让模型整篇乱写。

LumenX 证明从小说文本到短漫剧视频的全链路也已有开源实践，包含剧本分析、角色定制、分镜、资产、视频。这说明“剧本结构化”不是孤立玩具；它是下游分镜和资产生产的基础。

Sensor Tower 的短剧市场报告证明短剧消费市场有规模，内容供给链条有现实经济驱动。但这不证明单独卖一个 YAML 转换器就能商业化。正确判断是：下游短剧和剧本生产市场强；小说到结构化剧本是上游模块；它作为完整产品是否收费，还取决于是否接入编辑、审查、分镜、资产、导出、团队协作等工作流。

所以我们不应发明行业工作流。我们应继承行业对象：剧本元素、编剧室流程、故事圣经、节拍表、场景卡、修订和批注。我们可能主动设计的是：把这些对象放进一个低摩擦、可读、可查询、可投影、可校验的结构化书稿系统里，让执行者和模型都能工作。

## 十、YAML Schema 的设计理由应写成本体设计理由

甲方要求“写一篇文档，定义剧本 YAML Schema，并说明设计原因”。如果我们只写字段说明，质量不够。正确的 Schema 文档要说明字段来自哪个消费者动作。

例如：

`source_refs` 的存在理由不是“方便追溯”四个字，而是：总编剧和作者审查改编忠实度时，需要知道某个剧本场景依据了哪段原文；模型生成原创补充时，也必须标明不是原文事实。没有 `source_refs`，执行者的改编选择无法被审查。

`characters` 的存在理由是：台词、动作、人物关系和演员消费都依赖角色身份；未定义角色出现在场景中应被校验拦截。

`locations` 的存在理由是：场景标题、拍摄调度、美术、摄影和时间线连续性依赖地点对象。

`adaptation_brief` 或 `quality_rules` 的存在理由是：小说到剧本不是唯一映射；必须给执行者上位标准，否则输出只是模型任意选择。

`scene.elements` 的存在理由是：剧本正文是有顺序的动作、台词、括注、转场混合序列；拆成并列字段会丢失阅读和表演顺序。

`rationale` 的存在理由是：改编不是抽取，执行者会删改、合并、外化心理、原创过渡场景；这些选择必须给审查者理由。

`warnings` 或 `uncertainties` 的存在理由是：模型或人类执行者不能把未确认判断伪装成事实。未知要归档为未知。

`revision` 的存在理由是：剧本初稿会被打磨；公共契约要支持修改历史、批注状态和打回原因。

文档还应说明 YAML 只是投影，不是唯一写作面。若项目采用 AsciiDoc 书稿，Schema 文档应说：书稿中的 role、rel、payload 会投影成 YAML 的 types、relationships、metadata；YAML 用于甲方验收和机器交换；书稿用于人类阅读、编辑、批注和源文档维护。

---

## 十一、一个更成立的当前对象定义

现在可以重新定义这个题目的当前对象。

当前对象不是“AI 自动写剧本”。

当前对象是：

> 面向小说改编执行者的结构化剧本初稿生成系统。它读取多章节小说、改编总纲和书写本体约定，先建立可追溯的源材料、故事圣经、节拍和场景图，再由执行者生成剧本正文，并把书稿图投影成符合 Schema 的 YAML 剧本初稿。

这个定义里有几个构成性条件。

第一，必须有小说原文和章节边界。题面明确要求 3 章以上。

第二，必须有执行者工作协议。执行者可以是模型或人，但必须知道如何把小说信息转成剧本信息。

第三，必须有改编控制。没有总编剧标准，就不存在稳定质量。

第四，必须有结构化本体。否则 YAML 只是任意字段集合。

第五，必须有来源追溯。否则作者无法打磨，也无法知道执行者是否瞎编。

第六，必须有剧本正文元素。场景、动作、台词、括注、转场这些是剧本初稿最低要求。

第七，必须可校验。Schema、SHACL 或至少 Pydantic/JSON Schema 要检查结构完整性。

第八，必须可投影为 YAML。因为这是题面要求。

这些条件缺少任何一部分，对象都会变形。比如没有来源追溯，它只是生成器；没有改编控制，它只是随机写作器；没有剧本元素，它只是摘要；没有 YAML 投影，它不满足题面；没有可编辑书稿，它对作者打磨不友好。

---

## 十二、最小可行交付与完整愿景要分开

按照观察、判断与行动的框架，不能把未来愿景全部塞进当前承诺。

当前题面最小可行交付可以是：

1. 一个输入入口：读取至少 3 个章节的小说文本。
2. 一个改编总纲输入：可以默认生成，也可以让作者填写。
3. 一个结构化抽取流程：章节摘要、事件、角色、地点、关键物件。
4. 一个剧本生成流程：按场景输出动作、台词、旁白/画外音、转场、备注。
5. 一个来源追溯机制：每个场景或关键元素指向章节/片段。
6. 一个 YAML Schema：定义字段、类型、约束。
7. 一篇 Schema 设计文档：说明本体、消费者、设计原因。
8. 一个校验器：保证 YAML 可解析并符合 Schema。

更完整的愿景可以包括：

- AsciiDoc 书稿作为主编辑面。
- TTL/RDF 投影。
- OWL/RDFS/SKOS 词表。
- SHACL 形状校验。
- SPARQL 查询面。
- 批注和打回工作流。
- 与 Fountain/Final Draft 导出衔接。
- 与分镜、角色资产、视频生成衔接。
- Web UI 或图谱可视化。

这些愿景不是当前都要做。它们是期权式准备。当前设计可以保留稳定 ID、source_refs、role、rel、payload 这些接口，使未来能接上图谱和查询，但不提前承诺完整生产平台。

---

## 十三、这个项目里哪些东西不需要发明，哪些需要主动设计

不需要发明的东西：

剧本基本元素不用发明。场景标题、动作、角色名、台词、括注、转场、旁白、修订、批注，前人已经有成熟格式。

故事结构工具不用发明。Logline、synopsis、treatment、beat sheet、scene card、三幕式、Save the Cat、writer's room 白板卡片，这些都有成熟经验。

知识组织基础设施不用发明。AsciiDoc、Git、RDF、Turtle、OWL、SHACL、SPARQL、YAML、JSON Schema 都已有。

模型执行也不用神化。GPT、Claude、Gemini 只是执行者。我们不用发明“AI 工作流”，只要给执行者稳定上下文和校验。

需要主动设计的东西：

第一，当前项目的本体词表。哪些 role 存在？`.chapter`、`.source-snippet`、`.character`、`.location`、`.beat`、`.scene`、`.dialogue`、`.review-note` 是否够？哪些要进入最小集？

第二，当前项目的关系谓词。`adapted-from`、`depends-on`、`features-character`、`located-at`、`requires-prop`、`critiques`、`revises`、`constrains`、`derived-from-brief` 等如何定义？每个 rel 不能漂移。

第三，模型执行协议。每一步给模型什么输入，要求它输出什么结构，如何标记不确定，如何禁止把推断当事实。

第四，投影规则。AsciiDoc 书稿如何投影 TTL，TTL 或中间结构如何投影 YAML，YAML 字段如何对应本体。

第五，校验规则。哪些字段必填？哪些关系必须存在？未定义角色是否报错？场景无 source_refs 是否允许？原创场景是否必须有 rationale？

第六，Schema 文档叙述。它要解释设计原因，不是字段手册。每个主要字段都要说清消费者、动作、成本和验证。

## 十四、一个可工作的结构化书稿骨架

若采用 AsciiDoc 书稿，它可以像一本真正的改编工作书，而不是散乱文件。

顶层结构可以是：

```text
book.adoc
frontmatter/
  adaptation-brief.adoc
  schema-rationale.adoc
parts/
  100-source/
    010-chapter-001.adoc
    020-chapter-002.adoc
    030-chapter-003.adoc
  200-story-bible/
    010-characters.adoc
    020-locations.adoc
    030-world-rules.adoc
    040-timeline.adoc
  300-adaptation-structure/
    010-logline.adoc
    020-synopsis.adoc
    030-beats.adoc
    040-scene-cards.adoc
  400-script-draft/
    010-act-1.adoc
    020-act-2.adoc
  500-review/
    010-review-notes.adoc
backmatter/
  glossary.adoc
  ontology.adoc
  schema.adoc
```

源文档片段可以是：

```asciidoc
[#src-ch1-p12.source-snippet, chapter=ch1, start_line=120, end_line=134]
== 雨夜争吵原文片段

原文摘录或摘要。
```

角色可以是：

```asciidoc
[#char-liming.character, status=active]
== 李明

李明是主角。
他的创伤来源于 xref:src-ch1-p12[雨夜争吵原文片段, rel=derived-from]。

[#char-liming-profile.payload, for=char-liming, data=json]
[source,json]
----
{
  "want": "证明自己没有失败",
  "need": "承认自己仍在逃避父亲的评价",
  "voice": "短句，回避直接表达脆弱"
}
----
```

场景卡可以是：

```asciidoc
[#beat-003.beat, function=catalyst]
== 催化剂：李明收到旧怀表

本节拍改编自 xref:src-ch1-p12[原文片段, rel=adapted-from]。
它约束 xref:scene-004[办公室旧怀表场景, rel=constrains]。
```

剧本场景可以是：

```asciidoc
[#scene-004.scene, space=INT, location=loc-office, time=DAY, status=draft]
== 办公室旧怀表场景

本场景改编自 xref:src-ch1-p12[雨夜争吵原文片段, rel=adapted-from]。
本场景受 xref:beat-003[催化剂节拍, rel=depends-on] 约束。
本场景使用 xref:prop-watch[旧怀表, rel=requires-prop]。

李明坐在办公桌前。桌上放着一只旧怀表。

李明
你怎么会有这个？

[#scene-004-payload.payload, for=scene-004, data=json]
[source,json]
----
{
  "value_shift": {"start": "control", "end": "loss_of_control"},
  "rationale": "原文内心冲击被外化为旧怀表触发的停顿和追问。",
  "warnings": []
}
----
```

批注可以是：

```asciidoc
[#note-004-a.review-note, status=open, assigned_to=writer-a]
== scene-004 修改意见

这场戏的台词太直白。保留旧怀表动作，减少解释性台词。
本批注指向 xref:scene-004[办公室旧怀表场景, rel=critiques]。
```

这套写法不是发明剧本理论。它只是让已有工作流的对象变成可写、可读、可查、可投影。

## 十五、YAML 投影应该长什么样

YAML 不应直接模仿书稿的所有细节。它要服务甲方验收和下游机器读取。

一个合理的顶层可以是：

```yaml
schema_version: "1.0"
project:
  title: "..."
  adaptation_target: "screenplay_draft"
  language: "zh-CN"
adaptation_brief:
  format: "screenplay"
  tone: "..."
  fidelity_policy: "..."
  quality_rules: []
source:
  chapters: []
story_bible:
  characters: []
  locations: []
  props: []
  timeline_events: []
structure:
  logline: "..."
  synopsis: "..."
  beats: []
script:
  scenes: []
review:
  notes: []
metadata:
  generated_by: "..."
  generated_at: "..."
  warnings: []
```

每个 scene 至少应包含：

```yaml
id: scene-004
title: 办公室旧怀表场景
source_refs:
  - source_id: src-ch1-p12
    relation: adapted-from
setting:
  space: INT
  location_id: loc-office
  time_of_day: DAY
participants:
  - char-liming
required_props:
  - prop-watch
beats:
  - beat-003
elements:
  - type: action
    text: 李明坐在办公桌前。桌上放着一只旧怀表。
  - type: dialogue
    character_id: char-liming
    text: 你怎么会有这个？
rationale: 原文内心冲击被外化为旧怀表触发的停顿和追问。
status: draft
```

这不是最终答案，只是说明投影关系。真正设计 Schema 时，要避免字段无边界膨胀。当前题面最低需要 source、characters、locations、beats/scenes、elements、source_refs、rationale、warnings、metadata。制作拆解字段可以作为可选扩展，因为题面说“剧本初稿”，不说“制片拆解表”。但若我们从好莱坞工作流继承经验，Schema 文档应说明为什么保留 optional 的 props、production_notes 或 breakdown_hint：它们服务未来下游，不作为当前必要完成条件。

## 十六、模型执行流程应像员工工作流，而不是一次 prompt

一个可信流程可以分成几步。

第一步，建立输入书稿。把三章小说放进 source part，保留章节、段落、行号或片段 ID。

第二步，抽取源事实。模型或人类执行者从每章抽取事件、角色、地点、物件、时间线。输出必须区分原文事实和推断。

第三步，建立故事圣经。合并同一角色的别名，整理关系、地点、物件、世界规则。

第四步，生成或读取改编总纲。作者可以提供；如果作者不提供，模型可以先起草一份，但这份起草必须标记为待审查，不得冒充作者意图。

第五步，生成节拍和场景卡。每个节拍必须有 source_refs 或 rationale。原创节拍必须说明为什么补充。

第六步，生成剧本正文。按场景写 action/dialogue/parenthetical/transition。禁止把心理描写直接搬进 action；必须外化为可见/可听元素，或明确作为 VO/旁白策略。

第七步，校验结构。YAML 可解析；角色存在；地点存在；场景有来源或原创理由；台词有说话人；每个 scene 至少有 setting 和 elements。

第八步，审查和打回。总编剧或作者看 source_refs、rationale、场景文本和 warnings。通过、修改或打回。

第九步，投影。书稿投影 TTL/RDF 供查询，再投影 YAML 供甲方验收。也可以直接从内部模型投影 YAML，但书稿和图谱能提供更好的追溯与编辑面。

这个流程里，模型只是执行者。它可以参与每一步，但每一步都有输入、输出、约束和校验。它不是“自动生成完整答案”。

## 十七、哪些查询会直接体现“快速获得、可编辑、可打磨”

“快速”不是说模型几秒出稿。更有价值的快速，是作者和审查者能快速定位问题。

SPARQL/ARQ 或类似查询可以支持：

- 找出所有没有 source_refs 的场景。
- 找出所有原创场景及其 rationale。
- 找出所有被某条 review-note 批评的场景。
- 找出某个角色出现的所有场景。
- 找出某个道具被要求但未定义的场景。
- 找出所有 `status=draft` 且 assigned_to 某执行者的节点。
- 找出所有改编自第 2 章的场景。
- 找出所有包含 VFX 或预算风险的场景。
- 找出所有违反某条 QualityRule 的场景。
- 找出某个世界观规则约束了哪些场景。

这些查询直接降低认知负担。作者不需要在 YAML 里肉眼翻找。总编剧不需要问“谁写的、依据什么、为什么这样改”。执行者不需要靠记忆找上下文。机器也能把结构问题拦住。

这才是“可进一步打磨”的真实含义：不是给一份看似完整的剧本文本，而是给一份能被定位、能被追溯、能被批注、能被修改、能重新投影的结构化初稿。

## 十八、我对当前方向的判断

这个题目的甲方表述是模糊的，但不是没有方向。它把成熟行业里的大量工作压缩成“AI 辅助”“自动转换”“YAML Schema”。我们不能被这些词带偏。

真实对象应当是：

- 小说不是剧本，改编是信息熵降低和媒介转换。
- GPT/Claude/Gemini 不是魔法，是执行者。
- YAML 不是本体，是投影格式。
- Schema 文档不是字段说明，是本体设计理由。
- 作者可编辑不是靠 YAML 自然成立，而是靠书稿表面、追溯、批注和查询成立。
- 前人经验必须继承：编剧室流程、故事圣经、节拍表、场景卡、剧本元素、修订批注、剧本格式、制片拆解。
- 我们的主动设计点在于把这些对象组织成低摩擦、可查询、可校验、可投影的结构化工作流。
